# Deployment guide

## Targets and configuration

Create **separate staging and production** projects/resources. Proposed production Vercel projects: `apps/web` → `nammapros.in`, `apps/technician` → `pro.nammapros.in`, `apps/admin` → `admin.nammapros.in`, `apps/operations` → `ops.nammapros.in`; API → `api.nammapros.in`. These names are proposals, not verified DNS. Each Vercel project uses its app root, `npm ci` from monorepo root, and its own `npm run build`. Set `NEXT_PUBLIC_API_BASE_URL` to the matching HTTPS API origin; web also needs `NEXT_PUBLIC_SITE_URL` and server-only `API_BASE_URL`. Never place provider secrets in `NEXT_PUBLIC_` values. Configure production branch and protected preview environments in Vercel. Authenticated previews need same-site custom staging domains: unrelated `vercel.app` origins cannot rely on the production Lax-cookie strategy.

Use `services/api/.env.staging.example` or `.env.production.example` as a key list, and replace all `.invalid` examples. For provider configuration (Firebase, Razorpay, Cloudinary), refer to [Provider Integrations and Staging Guide](PROVIDER_INTEGRATIONS_STAGING_GUIDE.md). Cloud Run nonsecret values go into a reviewed copy of `infrastructure/deployment/cloud-run-env.yaml.example`. Secret Manager holds `DJANGO_SECRET_KEY`, `DATABASE_URL`, `REDIS_URL`, `FIREBASE_PROJECT_ID`, `FIREBASE_WEB_API_KEY`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, and any later messaging/SMTP credentials. `DATABASE_URL` should target the Cloud SQL Unix socket or a TLS-authenticated pooler; the default connection age is zero. Cap Cloud Run instances/workers against the Cloud SQL connection limit. `REDIS_URL` must be authenticated `rediss://`; configure private VPC egress. API cookies are host-only, Secure, HttpOnly, SameSite=Lax. The sibling `nammapros.in` sites can send credentials to `api.nammapros.in` with explicit CORS/CSRF origins. Confirm this on the owned domains before launch.

## Cloud resources and IAM

Before executing scripts, create Artifact Registry, Cloud SQL PostgreSQL, a TLS Redis service, a private GCS bucket, VPC connector, dedicated API/job service account, Scheduler caller account, and Secret Manager versions. Grant only required resource permissions: API/job account for Cloud SQL connection, relevant secret versions, and private bucket object operations; Scheduler account for the periodic job run action; build account for image publishing. Keep staging data and secrets separate. Never copy customer data into staging.

`infrastructure/deployment/deploy-cloud-run.sh` builds the image and deploys the public API service only after `NAMMAPROS_DEPLOY_APPROVED=yes`; it does not migrate the database. `deploy-periodic-job.sh` prepares a private periodic Job, a separate migration Job, and Cloud Scheduler. The job calls `run_periodic_jobs` once per minute, using Redis locks and task-level idempotency. This avoids a continuously running Celery worker but still incurs Scheduler, Job, VPC, Redis and Cloud SQL costs. Review quota, startup time and spend before activating it. The web service uses TCP probes; `/api/v1/health/` and database-backed `/api/v1/ready/` are available for external monitoring. Verify the actual domain before adding it to `DJANGO_ALLOWED_HOSTS`.

## Migration and recovery

Review `showmigrations --plan`, SQL for risky migrations, database size and lock risk in staging. Take and verify a Cloud SQL backup before a risky production migration. Apply schema changes with `run-migration.sh` only after separate `NAMMAPROS_MIGRATION_APPROVED=yes`; never from web startup or every replica. Prefer forward fixes for irreversible data changes, and keep the prior image available for rollback. Configure and verify backups/PITR with `configure-backups.sh` only after review. Restore only to a separate recovery instance first, verify application integrity, then plan a controlled cutover; never overwrite production during a drill. Set bucket public access prevention, uniform access and versioning with `configure-private-bucket.sh`; review retention and lifecycle before applying. Private documents are served by authorized Django endpoints; signed URLs are limited to ten minutes and need service-account signing permission if later used.

## Monitoring and release sequence

Send JSON stdout to Cloud Logging; request IDs are returned in `X-Request-ID`. Optionally set server-only `SENTRY_DSN` with PII disabled. Review `infrastructure/deployment/monitoring-alerts.yaml`, create Cloud Monitoring uptime/log/metric policies, and tune thresholds on staging. Alert on readiness, 5xx, job failures, reconciliation exceptions, webhook failures, repeated OTP failures, notification review backlog, and storage errors. Do not paste OTPs, bank details, KYC content or secrets into incident tickets.

Build and validate staging first. Configure required reviewers on the GitHub `production` environment; the workflow approval job itself never deploys. Verify Cloud SQL/Redis/GCS access, OTP, account roles, booking gates, KYC, notification templates, webhooks, refund reconciliation and recovery. Apply controlled migrations, then review the checklist. Production payment collection and payouts remain off until independent financial acceptance and explicit approval. Invoice issuance remains blocked pending approved legal/tax policy. DNS and production deployment require separate user approval.
