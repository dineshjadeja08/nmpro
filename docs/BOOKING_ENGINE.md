# Booking engine

Catalog services can have active packages with fixed or inspection pricing, duration, inclusions and exclusions. `PricingRule` is unique per active package/zone and stores all amounts as integer paise. Tax is an explicitly configured amount; no tax rate is inferred. A rule must explicitly allow `PAY_AT_VISIT` before confirmation can create `CONFIRMED_UNPAID`. `PREPAID` is blocked until verified payment integration exists.

An authenticated customer selects an owned address. Serviceability requires an active city and zone matching the address city/PIN, active service coverage, an active service/category/package and active pricing rule. Valid PIN syntax alone does not establish serviceability. Availability lists only explicitly active, non-blackout slots in the configured zone/package, after each slot's lead time, with remaining capacity. Package skill code is stored but technician-level scheduling is not implemented; operations must set capacity conservatively.

A hold locks the PostgreSQL slot row, counts unexpired active holds and confirmed unpaid bookings, rejects full capacity with HTTP 409, and expires after `BOOKING_HOLD_MINUTES` (default five). A Celery cleanup task marks expired rows, while every read/confirmation already checks the timestamp. A quote binds an owned hold to a rule/version, line items, total and expiry. Confirmation locks the customer, slot, hold and quote, rechecks serviceability and pricing, requires explicit accepted total and an `Idempotency-Key`, then writes booking, item, immutable snapshot, status event, audit event, idempotency record and outbox event in one transaction. Replays with the same key/body return the original booking; changed body returns 409.

Cancellation and rescheduling require cutoff windows explicitly stored in the booking snapshot. Cancellation changes status and frees capacity by excluding the booking from active occupancy. Rescheduling obtains a new hold, locks both slots in deterministic order, keeps the same package/address/zone and price, updates the booking, consumes the new hold, and records event/outbox/audit data atomically. If validation fails, the original booking stays unchanged.
