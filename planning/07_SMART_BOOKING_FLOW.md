# Smart booking flow contract

Existing path spans `F/src/features/bookings/components/booking-scheduling-shell.tsx`, `booking-review-shell.tsx`, B `apps/bookings/services.py` and `apps/payments/services.py`; the new flow is a redesign. Default UI uses one guided three-step route with URL/state restoration, no cart dependency.

| Step/state | UI and validation | API/transition | Failure and recovery |
|---|---|---|---|
| 1 SERVICE | Search/select service, category or diagnostic. Show starting price, inclusion, possible inspection fee; problem text <=1,000 chars. | GET `/api/v1/catalog`, `/services/{slug}`; optional POST `/booking-intents` draft. No inventory held. | No results -> diagnostic; retired service -> selection with explanation. |
| 2 ADDRESS | Choose saved or add validated Indian address/pincode and consent; serviceability must match service+zone. | GET `/addresses`, POST `/addresses`, POST `/serviceability/check`; GET `/availability?service_id&address_id&from&to`. | Geocode failure -> manual; zone unsupported -> alternative address/support. |
| 2 SLOT | Show backend slots and timezone Asia/Kolkata; user picks one. | POST `/slot-holds` under DB transaction, response `hold_id`, `expires_at`, `version`. Atomic capacity decrement/unique occupancy rule. | 409 taken -> refresh; 410 expired -> choose again; no slots -> next date/support. |
| 3 REVIEW | Quote line items in paise, tax, fee, inclusions, payment policy; edit returns to prior step. | POST `/quotes` using service/address/hold, immutable `quote_id`, price version and expiry. Server verifies catalogue and zone. | Price change -> explicit updated quote; no automatic charge. |
| 3 AUTH | OTP only if session absent or risk policy requires; returning user stays signed in. | Firebase phone token -> backend exchange; privileged staff separate. | OTP timeout/resend with rate limit; preserve draft/hold when possible. |
| 3 CONFIRM | One CTA with idempotency key. | POST `/bookings` binds quote+hold atomically into `AWAITING_PAYMENT` or policy-approved `CONFIRMED_UNPAID`. POST `/payments/orders`; provider callback is provisional; webhook/reconciliation transitions to `CONFIRMED`. | Retry with same key returns same booking/order; timeout polls GET booking/payment. Expired hold starts Step 2. Failed payment releases capacity after grace policy. Late capture -> refund or assisted reschedule. |
| AFTER | Reference, timeline, assignment, cancel/reschedule, invoice/support/rebook. | GET `/bookings/{id}`, POST `/cancel`, `/reschedule`; GET `/invoice`. | Unknown payment shows “checking”; never create a second booking. |

State machine: `DRAFT -> HELD -> AWAITING_PAYMENT -> CONFIRMED -> ASSIGNED -> EN_ROUTE -> ARRIVED -> IN_PROGRESS -> COMPLETED -> CLOSED`; branches `EXPIRED`, `PAYMENT_FAILED`, `CANCELLED`, `REFUND_PENDING`, `REFUNDED`. Pay-after-service is `CONFIRMED_UNPAID` under explicit policy. Keep payment state independent (`ORDER_CREATED`, `CAPTURED`, `FAILED`, `REFUND_PENDING`, `REFUNDED`). Transitions require expected version, actor permission, event and audit record. Holds have short configurable TTL (initial 10 minutes); expiration worker and on-read expiry enforce release. Count only active holds/confirmed occupancy. PostgreSQL row lock on slot or inventory counter ensures capacity. Quote/booking/order keys uniquely scoped to customer and request hash. Webhook event ID and provider payment ID unique. See `09_DATABASE_SCHEMA.md` and `10_API_SPECIFICATION.md`.

Quick Rebook fetches prior service/address identifiers, checks current eligibility, then calls fresh availability and quote. It never copies old slot, price or payment authorization. Measure 30–60-second target with client spans for steps and separately record OTP/provider wait.
