# Source-level security audit

Static findings only. Severity reflects plausible NammaPros impact; production configuration and exploitability require staging validation. Source references use B/F archive roots. No secrets are printed here. No dependency vulnerability scan was executed.

| ID/severity | Status, evidence, scenario/impact, remedy |
|---|---|
| S1 HIGH | **Confirmed design weakness**. `F/src/features/auth/storage.ts:3-29` keeps access and 7-day refresh JWTs in localStorage; `B/config/settings/base.py:216-226` sets lifetimes. Any successful script injection or malicious browser extension can read refresh token and impersonate user. Use a BFF or HttpOnly Secure SameSite refresh cookie with CSRF defense; short-lived access token in memory; revoke/rotate and test theft response. Priority P0. |
| S2 HIGH | **Confirmed authorization behavior**. `B/apps/accounts/staff_access.py:86-95` returns full access to an ADMIN with no groups or `Super Admin` group. Accidental group omission grants all admin routes including finance and staff. Default deny; explicit role grants per action/resource; separate Ops/Finance permissions; tests for missing and unknown groups. Priority P0. |
| S3 HIGH | **Confirmed availability integrity gap**. `B/apps/scheduling/services.py:20-27,39-51` counts all PENDING_PAYMENT bookings; `B/apps/bookings/services.py:46-68,135-158` creates them with no expiry. Abandoned checkout can exhaust a slot indefinitely; later payment can confirm against a stale appointment. Add expiring slot holds, transactionally reclaim, and reject/route late captures with refund or alternate slot. Priority P0. |
| S4 HIGH | **Potential financial integrity risk**. `B/apps/payments/services.py:85-120,223-286` validates HMAC and amount but source inspection did not establish provider-side capture fetch/reconciliation before final confirmation in every path. A valid signature is meaningful, yet asynchronous failed/refunded/captured order handling needs adversarial test. Verify capture status and order/customer/amount/currency, reconcile webhooks, immutable ledger. Priority P0. |
| S5 MEDIUM | **Confirmed reliability risk**. `B/apps/notifications/services.py:28-52`, `tasks.py:7-24` creates and sends inline after commit. Provider latency/failure can delay the API and lose retry continuity. Durable outbox + worker, delivery keys, bounded retries/dead-letter and alerting. Priority P1. |
| S6 MEDIUM | **Potential data exposure**. `B/apps/operations/views.py:727-735` exposes runtime configuration names/host lists to authorized admin; paired with S2, broad staff access can reveal operational topology. Reduce to safe health indicators and narrowly scope permission. Priority P1. |
| S7 MEDIUM | **Potential payment audit ambiguity**. `B/apps/bookings/services.py:418-438` and `B/apps/operations/services.py:595-605` mark manually recorded payments `signature_verified=True`, which does not mean provider signature verified. Separate `verification_method=OFFLINE_ATTESTED`, require dual control/evidence, immutable journal. Priority P1. |
| S8 MEDIUM | **Potential XSS exposure, no exploit confirmed**. F `src/app/layout.tsx:78-98` embeds static analytics script; `F/src/components/seo/json-ld.tsx:5-12` escapes `<` correctly. Third-party tags and localStorage token combination increase consequence of tag compromise. Adopt CSP/nonces, pin tag governance, remove browser refresh token. Priority P1. |
| S9 MEDIUM | **Potential upload risk**. `B/apps/technicians/serializers.py:354-375` checks size/MIME/header, and private-document routes exist; full malware scanning, quarantine, content disposition and retention were not established. Validate isolation with malicious polyglot files and signed access URLs. Priority P1. |
| S10 LOW | **Configuration verification**. `B/config/settings/production.py:46-71` sets TLS redirects, secure cookies, HSTS and required origin/host lists; `B/config/settings/base.py:154-190` configures CORS and throttling. Actual proxy trust, origin list and rate-limit behavior under scale are UNKNOWN. Stage tests required. Priority P2. |

Positive controls observed: Firebase token verification (`B/apps/accounts/auth/providers.py`), scoped customer booking queryset (`B/apps/bookings/views.py:174-180`), booking/slot row locks (`B/apps/scheduling/services.py:87-92`), HMAC comparison and webhook hash (`B/apps/payments/services.py`), upload signature checks, audit log model, and production fail-fast checks. These are source properties, not proof of production security. No SQL injection or definite IDOR was identified from sampled routes; complete negative authorization testing remains a release gate. OWASP-style SAST/SCA and penetration testing are required before launch.
