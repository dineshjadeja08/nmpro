# NammaPros audit decision

**Recommendation:** Use Purple Squad as a technical reference, not as the new product's direct codebase. Its Django/DRF API and Next frontend contain substantial working designs, tests and transaction patterns; the desired brand, booking journey, role separation and financial controls require an independent NammaPros build. Code/assets must be rights-cleared before reuse. The current production posture is UNKNOWN because this was static archive review only.

Actual stack: Python 3.12+, Django 5.2 range, DRF 3.17 range, PostgreSQL in production, Redis cache/throttle, Firebase, Razorpay, MSG91, Google Maps and Cloudinary; Next 16.3 range, React 19.2.8, TypeScript 5, Tailwind 4. The source contains 37 backend and 50 frontend test files, but no suite was run. Frontend and backend deployment instructions exist for multiple hosts; actual live environment is unverified.

Reuse candidates are **patterns after verification**: model boundaries, booking/assignment row locking, idempotency records, Razorpay HMAC verification, scoped customer queries, KYC header validation and OpenAPI structure. Refactor availability holds, auth/session, payment reconciliation, notifications, staff permissions and API contracts. Rebuild all four portal UIs; create quotation, ledger, payouts, support ticket lifecycle and controlled dispatch. No live customer/technician data transfer.

Key findings: pending-payment bookings consume capacity without expiry (`B/apps/scheduling/services.py:20-51`); refresh JWT is in browser localStorage (`F/src/features/auth/storage.ts:3-29`); ungrouped ADMIN staff gain broad access (`B/apps/accounts/staff_access.py:86-95`); notification delivery is synchronous (`B/apps/notifications/tasks.py:7-24`); dedicated finance/quotation models are absent. These are design and source findings, not measured production incidents. Further payment capture, permissions and upload checks require staging validation. Full findings and priority are in `03_SECURITY_AUDIT.md` and `04_PERFORMANCE_AUDIT.md`.

Recommended architecture: four small Next applications sharing tokens and API client, one modular Django API, PostgreSQL, Redis/Celery with durable outbox, isolated cloud environments and provider credentials. Booking is three guided steps: service, address/slot, review/confirm; server quote, expiring capacity hold, idempotent confirmation and provider-reconciled payment. Quick Rebook refreshes price and availability.

Timeline: phase 0 audit; phases 1–5 scaffold, design, auth/catalog/locations, smart booking, payments/notifications; phases 6–8 technician, operations and admin/finance; phase 9 hardening; phase 10 deployment/pilot. Controlled functional MVP estimated **6–8 weeks** with ready accounts and focused scope, plus **3–5 weeks** hardening/pilot evidence. A 3–5-week production launch is not supported by the audited gaps. Top risks are rights, capacity/payment races, staff privilege, financial reconciliation, KYC privacy and provider setup.

**First implementation task after audit review:** create a separate NammaPros repo with CI, four frontend shells, a modular Django API and local Postgres/Redis, plus typed API contracts. No application implementation was started in this phase.
